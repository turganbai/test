# Набор конфигурации Claude Code для команды

Три механизма и что в каком лежит:

| Механизм | Путь | Что кладём | Когда грузится |
|---|---|---|---|
| CLAUDE.md | `CLAUDE.md` (в репо), `~/.claude/CLAUDE.md` (личное) | факты и постоянные правила | каждая сессия |
| Rules | `.claude/rules/*.md` | тематические правила, можно с `paths:` | каждая сессия или при работе с matching-файлами |
| Skills | `.claude/skills/<name>/SKILL.md` | процедуры, чек-листы, workflow | только при вызове (`/name`) или когда модель сочтёт релевантным |

Быстрый старт: `/init` в корне репозитория сгенерирует черновой CLAUDE.md по кодовой базе,
дальше правьте руками. Проверить, что реально загрузилось в сессию — `/context`.

---

## 1. Шаблон `CLAUDE.md` (коммитится в репо)

Держите файл до ~200 строк. Пишите только то, что Claude не может вывести из кода сам:
подводные камни, причины решений, соглашения, отличающиеся от дефолтов инструментов.
Формулировки — проверяемые: «отступ 2 пробела», а не «форматируй аккуратно».

```markdown
# <Название проекта>

## Стек
- Язык/рантайм: <например, TypeScript 5.4, Node 20>
- Фреймворк: <...>
- Пакетный менеджер: pnpm (npm не использовать)
- База: <...>, миграции через <...>

## Команды
- Установка: `pnpm install`
- Тесты: `pnpm test` — запускать перед каждым коммитом
- Линт: `pnpm lint --fix`
- Локальный запуск: `pnpm dev` (нужен запущенный Redis)

## Где что лежит
- HTTP-хендлеры: `src/api/handlers/`
- Доменная логика: `src/domain/` — сюда не тащить зависимости от фреймворка
- Общие утилиты: `src/lib/`

## Соглашения
- Ошибки возвращаем в формате `{ code, message, details }`, не бросаем наружу raw-исключения
- Логирование только через `src/lib/logger.ts`, `console.log` в проде запрещён
- Новые эндпоинты — с валидацией входа и OpenAPI-комментарием

## Внутренние API и версии (чтобы не искать в вебе)
- Внутренний клиент биллинга: `@acme/billing-client` v3, доки: <ссылка/путь>
- Аутентификация: сервис <...>, контракт описан в `docs/auth.md`

## Workflow
- Коммиты и PR делаем прямо из сессии Claude Code, а не копированием диффа в другой терминал
- Крупные задачи — сначала plan mode, затем реализация промежуточными коммитами
- Между этапами задачи — `/clear` или `/compact`, не раздувать одну сессию
```

Заметки для людей можно оставлять в HTML-комментариях `<!-- ... -->` — они вырезаются
до попадания в контекст и не стоят токенов.

Личные предпочтения, не для команды, — в `~/.claude/CLAUDE.md` (все проекты)
или в `./CLAUDE.local.md` (этот проект, добавить в `.gitignore`).

Если в репозитории уже есть `AGENTS.md`, не дублируйте: создайте `CLAUDE.md` с одной
строкой `@AGENTS.md` и допишите под ней Claude-специфичное.

## 2. Path-scoped правила `.claude/rules/`

Файл грузится только когда Claude читает подходящие файлы — экономит контекст.

`.claude/rules/api.md`:

```markdown
---
paths:
  - "src/api/**/*.{ts,tsx}"
---

# Правила для API-слоя

- Каждый эндпоинт валидирует вход через zod-схему в `schemas/`
- Ответы об ошибках — только через `errorResponse()` из `src/lib/http.ts`
- Никаких прямых обращений к БД из хендлера: только через репозиторий из `src/domain/`
```

`.claude/rules/testing.md`:

```markdown
---
paths:
  - "**/*.test.ts"
---

# Тесты

- Фреймворк: vitest, моки — только `vi.mock`, sinon не использовать
- Один тест — один сценарий, без общего мутируемого состояния между кейсами
- Интеграционные тесты требуют локальный Redis: `docker compose up -d redis`
```

Личные правила для всех проектов — в `~/.claude/rules/`.

## 3. Скиллы

### `/ship` — коммит и PR из сессии

`.claude/skills/ship/SKILL.md`:

```markdown
---
description: Прогоняет проверки, коммитит и открывает PR по текущим изменениям.
disable-model-invocation: true
allowed-tools: Bash(git add *) Bash(git commit *) Bash(git status *) Bash(git diff *) Bash(gh pr create *) Bash(pnpm *)
---

## Текущее состояние

- Статус: !`git status --short`
- Диф: !`git diff HEAD`

## Задача

1. Прогони `pnpm lint` и `pnpm test`. Если что-то падает — остановись и покажи ошибку, дальше не иди.
2. Сгруппируй изменения в осмысленные коммиты (не один «wip» на всё).
   Сообщение: `<тип>(<область>): <что сделано>`, императив, до 72 символов в заголовке.
3. Открой PR через `gh pr create` с описанием: что меняется, зачем, как проверить.
4. Выведи ссылку на PR.

Если изменений нет — так и скажи, ничего не делай.
```

`disable-model-invocation: true` — чтобы Claude не решил закоммитить сам; вызов только руками.

### `/refactor-pass` — уборка вместо только-добавления

`.claude/skills/refactor-pass/SKILL.md`:

```markdown
---
description: Проход по недавним изменениям с прицелом на сокращение и удаление кода. Использовать после серии фич, когда накопилось дублирование.
---

Проанализируй код, изменённый в текущей ветке (`git diff main...HEAD --name-only`), и найди:

- дублирование, которое можно свести к одной функции
- мёртвый код: неиспользуемые экспорты, ветки, флаги, закомментированные блоки
- обёртки и слои абстракции, через которые проходит ровно один вызов
- зависимости из package.json, которые больше нигде не используются

Для каждой находки: путь, что предлагаешь удалить/объединить, чем рискуем.
Сначала покажи список, правки вноси только после подтверждения.
Приоритет — уменьшение количества строк без потери поведения; тесты должны остаться зелёными.
```

### `/context-check` — почему модель лезет в веб

`.claude/skills/context-check/SKILL.md`:

```markdown
---
description: Проверяет, чего не хватает в CLAUDE.md, из-за чего приходится искать в интернете то, что есть в проекте.
disable-model-invocation: true
---

Пройдись по репозиторию и текущему CLAUDE.md и составь список того, что модели
приходится выяснять заново каждую сессию:

1. Версии ключевых зависимостей и рантайма
2. Внутренние библиотеки и сервисы, у которых нет публичной документации
3. Нестандартные конвенции, отличающиеся от дефолтов инструментов
4. Команды сборки/тестов/запуска, включая внешние требования (БД, переменные окружения)

Выведи предлагаемые строки для CLAUDE.md. Файл не редактируй без подтверждения.
Помни про лимит ~200 строк: если предложений больше, часть вынеси в `.claude/rules/`
с `paths:` вместо добавления в основной файл.
```

## 4. Что раздать команде разово

- `CLAUDE.md` и `.claude/rules/` — в репозиторий, ревьюить как обычный код
- `.claude/skills/` — туда же, если workflow общий; личное — в `~/.claude/skills/`
- Организационные правила (безопасность, комплаенс) — managed CLAUDE.md,
  его нельзя отключить настройками пользователя:
  - macOS: `/Library/Application Support/ClaudeCode/CLAUDE.md`
  - Linux/WSL: `/etc/claude-code/CLAUDE.md`
  - Windows: `C:\Program Files\ClaudeCode\CLAUDE.md`

## 5. Важная оговорка

CLAUDE.md, rules и skills — это контекст, а не enforcement: Claude их читает и старается
следовать, но строгого соблюдения не гарантируется. Если что-то должно выполняться
обязательно (запретить команду, прогнать линт перед коммитом) — это PreToolUse hook
или `permissions.deny` в настройках, а не строчка в CLAUDE.md.

Отдельно: метрики из аналитики — материал для разговора, а не цель. Скиллы и правила
стоит писать под реальные боли команды, а не под то, чтобы «поднять» distinct_skills_used_count.
```
